# Security model

| Asset | Protection |
|---|---|
| Identity key | Generated on device; stored only wrapped (XChaCha20-Poly1305) by a key from Argon2id(passphrase, 64 MiB) or the OS keychain. Never transmitted. |
| Messages in transit | QUIC + TLS 1.3 with certificate = identity key, pinned by the dialer (no CA, no MITM by signaling/relays). Signed by author (Ed25519) so they can be relayed/gossiped safely. |
| Offline mail | Sealed to the recipient (ephemeral X25519 + XChaCha20-Poly1305) and signed inside; mailboxes (friends / relays) see random bytes. |
| Group content | Epoch key per group, rotated on member removal/leave; new keys sealed per member and checked against the signed `Rekey` commitment. Concurrent rotations resolve the same on every member (lowest `(hlc, author, id, sig)` wins the epoch; losers' keys are kept only to read what was sent under them); a removal is covered only by a later winning rotation of its remover (or of the owner when the remover can't), so a key a concurrent rotation handed to the removed member is replaced. Keys arriving before their `Rekey` are kept (bounded per sender) until it comes; a member at an epoch without its key asks members (`Ext GROUP_KEY_REQUEST`, answered only to current key holders for epochs since they joined). Remote clocks move ours by ≤ 2 min; ops dated > 10 min ahead are refused on publish and receive. |
| Local data | SQLCipher (AES-256-CBC + HMAC-SHA512 per page), `secure_delete=ON`, optional per-chat retention including "no history" (wiped at start). |
| Remote control | Password never sent: challenge/response with BLAKE3-keyed proof bound to both devices; exponential lock-out after 5 failures; host must accept unless unattended + fixed password or explicitly trusted. Since protocol 3 the fixed (unattended) password is stored only as a verifier — the Ed25519 public key of `Argon2id(password, salt, 19 MiB, t=2)` — and v3 viewers sign the challenge (`RemoteChallengeV2` carries salt + KDF parameters), so a copy of the host's data contains nothing that logs in. Older viewers only get the temporary password. |
| Multi-device | The account key stays on the main device; other devices have their own keys and a root-signed certificate (TLS SAN + 170-byte device signatures in the existing `sig` fields). Linking: QR secret or 12-digit code via SPAKE2 (one online guess per session, code rotates after 3 failures), both bound to the TLS channel. The device showing the QR / code reveals its addresses only to the device that proved the secret first — over sealed signaling mail (`Ext LINK_PRE`, QR proof or SPAKE2 + key confirmation, counted with the other guesses, ≤ 10 attempts/min) — and the scanning device doesn't dial a rendezvous candidate before that (LAN beacon candidates excepted: LAN addresses only). The rendezvous tag hashes the first 6 of the 12 digits: grinding it offline yields at most those 6, the other 10⁶ stay for the online PAKE. Device lists: an account signs its own list, and anyone can make an account, so a listed device counts only with **its own acceptance signature** for that account in its entry (`DeviceEntry.proof`, sent in `LinkInfo` when linking; older linked devices send it with `Ext DEVICE_ACCEPT`) or if it already presented a certificate of that account to us; a device known under one account is never re-assigned to another; a revocation only touches devices that were that account's; lists of strangers are dropped (only my own, friends', people I asked and reachable group co-members' are kept). Self-sync and history only travel between devices whose certificates name the same account. Revocation: a new root-signed list; everyone holding it refuses the device (connections closed, its signatures dropped, nothing queued for it), its ratchet sessions are dropped and group keys rotate (by the account if admin, else an admin on `GroupRekeyRequest`); the device wipes the account's data on its next start. Window: a sender holding an older list may still deliver to the revoked device until it hears the new one (device lists travel on every connection and as mail). A lost **main** device means the account key may be exposed (same as before multi-device): protect it with a passphrase and promote another device with the recovery phrase — the old main device signs out when it sees the newer list. Linked devices reach old-app friends via the main device, which only re-signs content a current device of the account signed. See [Multi-device](multi-device.md). |
| Signaling metadata | **DHT**: there is no public record any more. The only record (salt `lumora-f2`, addresses + public relays) is encrypted with a random per-device "friends-only key" handed only to friends and own devices (`Ext DHT_KEY`, v3) and rotated when someone leaves your friends — and it is *stored under* (signed by) an Ed25519 key derived from that key, never the identity key, so DHT nodes see "some key's record published from IP Y" but can't compute which Lumora ID it belongs to. The multi-device record (main device, ≥ 2 devices) is stored the same way. **Nostr**: ephemeral events from throw-away keys. Friends post to me under a tag derived from my friends-only key, rotating daily (I listen to yesterday's/today's/tomorrow's, and to the previous key's for a week after a rotation) — unlinkable to my ID without the key. Strangers' first contact (friend requests, remote-control pre-authentication, device linking) needs a tag anyone can compute from my ID (`inbox_tag`): I subscribe to it **only while "Let strangers find me by ID" is on** (or a device link is pending), and only on a random 2 of the configured relays (senders post to all). Limit: while it is on, those relay operators can see that "the device with ID X subscribes from IP Y". Lumora relay servers (`--relay`, user-configured) always see the key and IP of the devices connected to them. |
| IP addresses | Only people allowed to connect directly learn them: friends, people you sent a request to, your own devices, co-members of a **private** group you are in yourself (a group you left or were removed from no longer counts), the owner/admins of a **public** group you are in (ordinary members of a public group — anyone can join one — are strangers: they reach each other through relays / sealed mail and the group's gossip), a remote-control partner after the host accepts / the viewer proved the password (address-less pre-authentication over sealed signaling, `Ext REMOTE_PRE_*`), the device being linked once it proved the QR / code (see Multi-device), and devices you dialed yourself in the last 10 min (your offer carried your addresses anyway). Gate: `Node::may_reveal_addrs` — every dial path goes through it (connect, the reconnect sweep, `resume`, upgrades, path repair). A stranger's offer (also a pending requester's) gets no answer with addresses and no packet: at most a relay-only answer naming relays the user configured (never a friend's peer relay, never one a stranger named — strangers' relay hints are never followed or advertised). Strangers' addresses are never cached, they are never dialed, punched, sprayed or upgraded to a direct path; their requests reach you as sealed signaling mail (Nostr, ephemeral), relay mailboxes or friends' store-and-forward, retried from the outbox (2 min → 1 h). `Hello` carries `app`/`os` only for friends and own devices. No silent contact rows for strangers, and nothing else persisted for them either (protocol version, device lists, rate-limit state live in bounded in-memory caches). Offers are deduplicated (strangers in a cache of their own) and checked against replays (per-device timestamps; a "repair" offer must be newer than the connection it repairs). |
| Store-and-forward | A friend keeping offline mail (`StoreFor`) learns who gets mail from you and when. It is handed only to your own devices and to friends who, as far as you can tell, already know the recipient (a private group the three of you share); otherwise only relay mailboxes / Nostr carry it (sealed: they see random bytes for a key). |
| LAN / IPv6 | LAN announcements (multicast `LMRH`, mDNS) carry only a daily-rotating hint of the key (`lan_hint`), recognisable only by someone who already knows you, and only LAN addresses; the legacy `LMRA` (key in clear) is still accepted, never sent. Link beacons carry no public address. IPv6 addresses whose interface id embeds the hardware address (EUI-64) are never offered; temporary addresses are preferred. |
| Directory | "Let strangers find me by ID" (Settings › Privacy, kv `privacy.discoverable`, default on): when off, the short-ID record is replaced by a tombstone. Limit: while it is on, the directory can be enumerated (it is a public list of short ID → public key). |

## Threats considered
* **Malicious relay / signaling operator** → cannot read or forge; can drop traffic (other paths exist).
* **Network attacker (MITM)** → defeated by key pinning; users can compare the 60-digit safety number.
* **Stolen device (powered off)** → DB and keys encrypted; with a passphrase nothing on disk opens them.
* **Malicious group member** → can only act within role permissions; forged ops/messages fail signature checks.
* **Brute-force remote password** → lock-out, 31-symbol × 6 temporary passwords rotate per launch.
* **IP harvesting by strangers** (knowing only a short ID / @username / public key) → no addresses in answers, DHT, beacons or LAN packets; see "IP addresses" above. Friends, private-group co-members, public-group admins and bots you use can see your IP by design (direct P2P; there is no default relay/TURN server).
* **Device-list forgery** (a stranger or friend signs a list naming someone else's device as theirs or as revoked, to cut them off / steal their mail) → lists of strangers are dropped; a device is bound to an account only with its own acceptance signature or certificate, never re-assigned; revocations only apply to the account's own devices.
* **Floods** → signals are handled by ≤ 64 tasks at once (more are dropped, senders retry), Nostr query results are capped (count and bytes, 256 KB messages), relayed virtual addresses live in a bounded LRU.

## Known limits (honest)
* With "Let strangers find me by ID" on (default), the Nostr operators carrying my public inbox (2 random relays) can link my ID to my IP; a configured Lumora relay server always can. Turning it off keeps friends working (friends' inbox, DHT friends-only record) but strangers can reach you only through a relay mailbox.
* Friends' Nostr tags and the DHT record rotate only when someone leaves your friends (tags also daily): a former friend who kept the old key can still post to the previous key's inbox for a week (sealed signaling only — never answered with addresses).
* Ordinary members of public groups don't connect directly: their traffic is relayed / mailed (slower), by design.
* 1-1 chats use a Double Ratchet (Olm, via the audited `vodozemac` crate; `node/olm.rs`): a new key per
  message, forward secrecy and post-compromise security, also for mail stored offline. Sessions are made
  only with friends, your own devices and group co-members. The Olm account is pickled encrypted in the
  local database; a stolen *unlocked* database still exposes the stored history.
* Group encryption is sender-key style, not full MLS (RFC 9420). Planned.
* A compromised *running* device exposes everything that device can read — like any messenger.
